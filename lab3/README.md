## Цель и задание

Приобрести практические навыки создания потоков операционной системы, распределения работы между ними и синхронизации их выполнения.

По варианту № 17 необходимо **найти минимальный и максимальный элементы большого целочисленного массива** в многопоточном режиме. Максимальное количество одновременно используемых рабочих потоков задаётся ключом запуска. Требуется продемонстрировать количество потоков стандартными средствами ОС и исследовать зависимость **ускорения и эффективности** от размера массива и числа потоков.

## Реализация

Программа состоит из главного и нескольких рабочих потоков в рамках **одного процесса**:

- **Главный поток (`main`)** — разбирает аргументы, выделяет и заполняет массив, распределяет участки между потоками, вызывает `pthread_create()`, ожидает их завершения через `pthread_join()`, объединяет результаты и освобождает память.
- **Рабочий поток (`minmax_worker`)** — получает указатель на собственный участок исходного массива и вычисляет локальные минимум и максимум функцией `find_minmax()`.

Схема обработки:

```text
                       main
                          │
                массив из N элементов
                          │
              разбиение на P участков
                          │
          ┌───────────────┼───────────────┐
          │               │               │
        поток 1         поток 2         поток P
          │               │               │
       min₁, max₁      min₂, max₂      minₚ, maxₚ
          │               │               │
          └───────────────┼───────────────┘
                          │
                     pthread_join
                          │
                min(minᵢ), max(maxᵢ)
```

Массив не копируется: каждый поток получает указатель на начало своей части (`array + offset`) и её длину. При делении `N` элементов на `P` потоков каждый обрабатывает `N / P` элементов, а остаток распределяется по одному элементу первым потокам. Фактическое количество рабочих потоков равно `min(P, N)`, поэтому пустых участков не возникает.

Каждому рабочему потоку соответствует отдельная структура `MinMaxTask` с собственным результатом и статусом. Исходный массив потоки **только читают**, а свои результаты записывают в разные структуры. Главный поток объединяет результаты после `pthread_join()`. Поэтому для вычисления минимума и максимума **мьютексы не требуются**; гонки записи в общую переменную отсутствуют по архитектуре.

Основные интерфейсы:

| Функция / механизм | Назначение |
| --- | --- |
| `pthread_create()` | Создание рабочего потока |
| `pthread_join()` | Ожидание завершения потока и синхронизация результатов |
| `malloc()`, `calloc()`, `free()` | Динамическая память под исходный массив, идентификаторы и задания потоков |
| `clock_gettime(CLOCK_MONOTONIC)` | Измерение времени параллельного поиска |
| `syscall(SYS_gettid)`, `getpid()` | Получение идентификаторов потока и процесса в диагностическом режиме |
| `nanosleep()` | Искусственная задержка рабочих потоков только в режиме демонстрации |
| `strtol()`, `strtoull()` | Разбор и проверка аргументов запуска |
| `perror()`, `strerror()` | Сообщения об ошибках |

При обычном завершении выделенная память освобождается. Проверяются ошибки выделения памяти, создания и ожидания потоков, системных вызовов и неверных аргументов запуска.

## Сборка и запуск

Команды выполняются **в терминале WSL из корня** `~/projects/os_labs/lab3`:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
./build/lab3 --threads 4 --size 10000000
```

Аргументы передаются в указанном порядке:

```text
./build/lab3 --threads N --size M [--verbose|--demo]
```

- `--threads N` — запрошенное максимальное количество рабочих потоков (`N > 0`).
- `--size M` — количество элементов массива (`M > 0`).
- `--verbose` — вывести PID/TID и локальные результаты потоков **после** завершения вычислений.
- `--demo` — оставить рабочие потоки живыми примерно на 12 секунд для наблюдения через `ps` и `strace`; время выполнения в этом режиме **не используется для оценки производительности**.

Числа массива генерируются с фиксированным начальным значением `srand(42)`, поэтому при одинаковом размере массива на той же реализации стандартной библиотеки исходные данные повторяются. Генерация выполняется **до** включения таймера.

## Контрольный запуск

Обычный режим:

```bash
./build/lab3 --threads 4 --size 1000000
```

В проведённом эксперименте получены:

```text
Array size: 1000000
Worker threads: 4
Minimum: -1073738226
Maximum: 1073740217
```

Время в строке `Elapsed time` зависит от нагрузки и не является фиксированным ожидаемым значением. Результаты min/max не должны изменяться при смене количества потоков для одного размера массива.

Подробный вывод:

```bash
./build/lab3 --threads 4 --size 1000000 --verbose
```

В этом режиме отображаются PID процесса и TID каждого рабочего потока. PID у них общий, TID различаются. Порядок создания потоков не гарантирует одновременного выполнения вычислений.

## Проверка корректности и обработка ошибок

### 1. Проверки с Sanitizers

Отдельная Debug-сборка с AddressSanitizer и UndefinedBehaviorSanitizer:

```bash
cmake -S . -B build-asan \
  -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_C_FLAGS="-fsanitize=address,undefined -fno-omit-frame-pointer" \
  -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address,undefined"
cmake --build build-asan

./build-asan/lab3 --threads 1 --size 1
./build-asan/lab3 --threads 16 --size 3
./build-asan/lab3 --threads 4 --size 1000000
./build-asan/lab3 --threads 16 --size 10000000
```

В выполненных проверках Sanitizers **не сообщили об ошибках**. Для одного элемента минимум равен максимуму. При `--threads 16 --size 3` программа запускает только **три** рабочих потока.

### 2. Некорректные параметры

```bash
./build/lab3 --threads 0 --size 100
./build/lab3 --threads -2 --size 100
./build/lab3 --threads abc --size 100
./build/lab3 --threads 4 --size 0
./build/lab3 --threads 4 --size -100
```

Первые три команды завершаются с сообщением `Invalid thread count`, последние две — `invalid array size`. Программа отклоняет некорректный ввод до запуска рабочих потоков.

## Диагностика потоков и системных вызовов

В Linux/WSL для демонстрации работы программы используются `ps` и `strace`. Идентификаторы процессов, потоков и адреса памяти при повторных запусках будут другими.

### 1. Наблюдение потоков через ps

```bash
./build/lab3 --threads 8 --size 1000000 --demo &
pid=$!
sleep 2
ps -T -p "$pid" -o pid,spid,stat,comm
wait "$pid"
```

В проведённом эксперименте был обнаружен **один процесс PID 4098** и **восемь рабочих потоков TID 4100–4107**. `ps -T` показал девять строк: главный поток плюс восемь рабочих. Состояние `Sl` соответствует ожиданию и признаку многопоточности. В режиме `--demo` потоки искусственно ожидают, поэтому эта проверка подтверждает **одновременное существование потоков**, а не непрерывное выполнение вычислений на всех ядрах.

### 2. Трассировка через strace

```bash
strace -f \
  -e trace=clone,clone3,futex,clock_nanosleep \
  -o strace.log \
  ./build/lab3 --threads 4 --size 1000000 --demo

grep -E 'clone|futex|clock_nanosleep' strace.log | head -n 40
```

В сохранённом опыте главный поток **PID/TID 4653** создал четыре рабочих потока **4654–4657** через `clone3()`. Флаги `CLONE_VM` и `CLONE_THREAD` показывают, что потоки разделяют адресное пространство и принадлежат одному процессу. `futex()` использовался при ожидании завершения, `clock_nanosleep()` — для задержки в демонстрационном режиме. Вызовы `pthread_create()` и `pthread_join()` относятся к POSIX API; в трассе видны системные механизмы Linux, через которые их реализует библиотека.

## Исследование производительности

Измеряется время от начала создания рабочих потоков до завершения ожидания и объединения результатов. Время **выделения и заполнения исходного массива**, а также печать итогов в измерение не включаются. Для исследования используется Release-сборка без `--verbose`, `--demo` и Sanitizers.

Проверены **5 размеров массива** (100 тыс., 1 млн, 10 млн, 50 млн и 100 млн элементов), **5 конфигураций** (1, 2, 4, 8 и 16 рабочих потоков), по **7 запусков** каждой — всего **175 измерений**. Для каждой конфигурации взята медиана времени. Фоновая нагрузка на ноутбук была минимизирована.

Медианное время выполнения, **мс**:

| Размер массива | 1 поток | 2 потока | 4 потока | 8 потоков | 16 потоков |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100 тыс. | **0,391** | 0,400 | 0,603 | 1,090 | 2,185 |
| 1 млн | 0,936 | **0,737** | 0,868 | 1,379 | 2,475 |
| 10 млн | 6,012 | 3,597 | **2,523** | 2,648 | 3,115 |
| 50 млн | 27,490 | 14,209 | 8,143 | **7,887** | 9,094 |
| 100 млн | 61,453 | 27,582 | 15,521 | **14,123** | 17,759 |

Ускорение и эффективность вычисляются по формулам:

```text
S(P) = T(1) / T(P)
E(P) = S(P) / P × 100%
```

Здесь `T(1)` — время **той же программы с одним рабочим потоком**, а не отдельной программы без pthread. Для массива из **100 млн элементов** получено ускорение **4,35 раза** на **8 потоках** (`61,453 / 14,123` мс), эффективность **54,4%**. При 16 потоках время выросло до **17,759 мс**.

На массивах малого размера накладные расходы на создание и ожидание потоков могут превышать пользу от параллельной обработки. С увеличением размера массива многопоточность становится выгоднее, но ускорение ограничивается затратами на потоки, кэшированием, пропускной способностью памяти и особенностями планирования. Показатель эффективности выше 100% в одной конфигурации (100 млн элементов, 2 потока) следует интерпретировать осторожно из-за вариации замеров и эффектов аппаратной платформы.

Графики ускорения и эффективности, исходные скриншоты диагностики и подробное объяснение результатов приведены в отчёте.

## Ограничения и воспроизводимость

- Запуск реализован под POSIX/Linux (тестирование — Ubuntu в WSL2); программа не является нативным приложением Win32.
- Параметры `--threads` и `--size` должны идти в указанном порядке. Одновременно использовать `--verbose` и `--demo` текущий интерфейс не позволяет.
- На небольших массивах время может быть сопоставимо с накладными расходами создания потоков; результаты отдельных запусков зависят от планировщика ОС и нагрузки системы.
- Режим `--demo` предназначен **только** для диагностики: искусственное ожидание не входит в результаты бенчмарка.
- Отсутствие сообщений Sanitizers в выполненных сценариях не является доказательством отсутствия любых ошибок.
