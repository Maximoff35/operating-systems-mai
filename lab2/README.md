# Лабораторная работа 2 — вариант 17

Попков Максим Александрович, М8О-205БВ-25. Windows 10/11, C11, Win32 API.

Родитель создаёт два дочерних процесса. Первые две введённые строки — имена выходных файлов child1 и child2. Следующие строки: длина **не больше 10 символов** → pipe1 → child1; **больше 10** → pipe2 → child2. Потомки удаляют английские AEIOU/aeiou и русские АЕЁИОУЫЭЮЯ/аеёиоуыэюя и выводят результат в stdout, перенаправленный в соответствующий файл. Y/y сохраняется. Перевод строки в длину не входит, пробелы входят. Unicode считается по кодовым точкам, включая корректный подсчёт emoji; составные графемы могут занимать несколько кодовых точек.

```text
                                   pipe1 → stdin child1 → удаление гласных → stdout → short.txt
пользователь → stdin parent → длина
                                   pipe2 → stdin child2 → удаление гласных → stdout → long.txt
```

## Сборка и запуск

Из папки `D:\code\os_labs\lab2_17` в PowerShell:

```powershell
cmake -S . -B build -G Ninja -DCMAKE_C_COMPILER=C:/mingw64/bin/gcc.exe
cmake --build build
.\build\parent.exe
```

Если программы уже собраны, достаточно последней команды. Не начинайте с исходной lab2.

Введите по очереди (без кавычек):

```text
short.txt
long.txt
Hello
abcdefghij
abcdefghijk
Operating systems
AEIOUaeiou
1234567890
12345678901
```

После последней строки нажмите **Ctrl+Z, затем Enter** для EOF. Без EOF дети продолжают ждать новые строки — это нормальная работа, а не зависание. Выходные файлы создаются заново, существующее содержимое стирается.

Проверка:

```powershell
Get-Content .\short.txt -Encoding utf8
Get-Content .\long.txt -Encoding utf8
```

Ожидаемый short.txt: `Hll`, `bcdfghj`, пустая строка (из AEIOUaeiou), `1234567890`.
Ожидаемый long.txt: `bcdfghjk`, `prtng systms`, `12345678901`.

Автоматический пример без ручного набора (PowerShell):

```powershell
Get-Content .\demo_input.txt -Encoding utf8 | .\build\parent.exe
```

UTF-8 файлы: без BOM. Для автоматических тестов с русскими строками требуется, чтобы PowerShell передавал UTF-8 (`$OutputEncoding = [System.Text.UTF8Encoding]::new($false)`). Интерактивный запуск сам переключает кодировку консоли в UTF-8 и восстанавливает её при выходе. Ограничение путей — MAX_PATH.

## Какие скриншоты сделать

1. **Терминал:** запуск, PID всех трёх процессов и маршрутизация строк, особенно длина 10 → child1 и 11 → child2. Ниже команды Get-Content и содержимое обоих файлов.
2. **Process Monitor → Ctrl+T:** дерево parent.exe → child1.exe и child2.exe. Для удобства откройте дерево, пока программа ждёт текст или EOF; фильтр «только ещё работающие» тогда подходит.
3. **Журнал Process Monitor:** WriteFile родителя в `\Device\NamedPipe`, ReadFile потомков из pipe, WriteFile child1 в short.txt и child2 в long.txt, Process Exit после EOF.

Перед опытом: Ctrl+E остановить, Ctrl+X очистить, Ctrl+L добавить три фильтра Include по Process Name: parent.exe, child1.exe, child2.exe. Запустить запись Ctrl+E, провести опыт, остановить. Отдельный канал child → parent отсутствует: в этом варианте результаты пишутся в файлы.

Скриншоты вставить в отчёт в раздел диагностики. Они не создавались автоматически и не подменены изображениями от варианта 6.

## Что говорить на защите

- Родитель **не удаляет гласные**: он читает строку, считает символы и выбирает один из двух каналов.
- Потомки используют одинаковый алгоритм, поэтому child1.exe и child2.exe собираются из общего child.c, но запускаются отдельными процессами с разными stdin/stdout.
- Вход каждого потомка — читающий конец своего pipe; выход — отдельный файл. stderr остаётся диагностическим потоком.
- Родитель создаёт и запускает детей по очереди. К моменту запуска второго handles первого, которые не должны наследоваться, уже закрыты или не наследуемы. Поэтому дети не удерживают чужие концы pipe.
- `SetHandleInformation` запрещает потомкам наследовать пишущий конец. Иначе они могли бы сами удерживать свои каналы открытыми и не получать EOF.
- Родитель закрывает **оба** пишущих конца до ожидания. Дети дочитывают данные, получают EOF, завершаются. Затем родитель проверяет их exit codes и закрывает handles процессов и начальных потоков.
- Один WriteFile не равен одной строке при чтении: pipe передаёт байты; строки восстанавливаются чтением до LF.
- `write_all` повторяет запись до передачи всех байтов и проверяет ошибки; строка может быть длиннее буфера канала.
- Длина считается до удаления гласных, иначе маршрутизация была бы неверной.
