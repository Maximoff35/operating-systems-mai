## Цель и задание

Приобрести практические навыки управления процессами в операционной системе и обмена данными между ними с использованием каналов (`pipe`).

По варианту № 6 родительский процесс запускает дочерний, перенаправляет его стандартный ввод на текстовый файл, а стандартный вывод — в канал. Дочерний процесс читает из файла строки с произвольным количеством целых чисел (`int`), вычисляет сумму чисел в каждой строке и передаёт результаты родителю. Родитель считывает данные из канала и выводит их в консоль.

**Среда выполнения:** Windows 11. **Язык:** C11. **Системный интерфейс:** Win32 API. **Сборка:** CMake, GCC (MSYS2) и Ninja.

## Реализация

Используются две самостоятельные программы:

- **`parent.exe`** — запрашивает имя входного файла, открывает его, создаёт канал и дочерний процесс, получает результаты вычислений и выводит их в консоль.
- **`child.exe`** — читает числа из стандартного ввода, суммирует их построчно и записывает результаты в стандартный вывод.

Схема передачи данных:

```text
input.txt ──(перенаправленный stdin)──> child.exe
                                         │
                                    вычисление сумм
                                         │
                                   stdout (pipe)
                                         │
                                         ▼
                                     parent.exe
                                         │
                                         ▼
                                  вывод в консоль
```

Файл передаётся дочернему процессу через наследуемый дескриптор стандартного ввода. Результаты передаются через **анонимный канал**, созданный `CreatePipe`. Для перенаправления потоков применяется `STARTF_USESTDHANDLES` при вызове `CreateProcessA`.

Ключевые функции Win32 API:

| Функция | Назначение |
| --- | --- |
| `CreateFileA` | Открытие входного файла |
| `CreatePipe` | Создание канала между процессами |
| `SetHandleInformation` | Запрет наследования читающего конца канала дочерним процессом |
| `CreateProcessA` | Запуск дочерней программы с перенаправленными стандартными потоками |
| `ReadFile` | Чтение результатов из канала родительским процессом |
| `WaitForSingleObject` | Ожидание завершения дочернего процесса |
| `GetExitCodeProcess` | Проверка кода завершения дочернего процесса |
| `CloseHandle` | Освобождение дескрипторов объектов ОС |

В программе проверяются результаты системных вызовов и ошибки обработки входных данных. Родитель закрывает ненужные дескрипторы канала; дочерний процесс освобождает память, выделенную для чтения строк произвольной длины.

## Сборка и запуск

Для сборки необходимы **CMake**, **Ninja** и компилятор **GCC** (например, из MSYS2 UCRT64). Команды выполняются в PowerShell из каталога лабораторной работы:

```powershell
cmake -S . -B build -G Ninja -DCMAKE_C_COMPILER=gcc
cmake --build build
.\build\parent.exe
```

После запуска ввести имя файла `input.txt`. Пример успешного выполнения (PID относятся к конкретному запуску):

```text
Enter input filename (for example, input.txt): input.txt
Parent PID: 23264
Child PID: 7272
Results:
Line 1: 60
Line 2: 20
Line 3: 50
Line 4: 42
```

Содержимое `input.txt`:

```text
10 20 30
5 7 8
100 -30 -20
42
```

Результаты соответствуют суммам чисел в каждой строке. Идентификаторы процессов при новом запуске будут другими.

Если Ninja отсутствует, но установлен `mingw32-make`, возможна сборка через `-G "MinGW Makefiles"` в отдельную папку сборки.

## Проверка обработки ошибок

Повторно запустить `parent.exe` и ввести:

- **`missing.txt`** — программа сообщит об ошибке `CreateFileA`, поскольку файл отсутствует.
- **`invalid.txt`** — дочерний процесс обнаружит некорректный элемент `wrong` во второй строке, передаст сообщение об ошибке по каналу и завершится с ненулевым кодом. Родитель обнаружит этот код завершения.

Результаты предыдущих строк выводятся до сообщения об ошибке. Входной файл читается в бинарном режиме: байты NUL (`0x00`) и Ctrl+Z (`0x1A`) считаются ошибкой с указанием номера строки, а не концом данных. Обычные окончания строк LF и CRLF поддерживаются. Родитель передаёт прочитанные из канала байты в stdout без повторного преобразования окончаний строк.

## Диагностика в Process Monitor

Используется **Microsoft Sysinternals Process Monitor**: https://learn.microsoft.com/en-us/sysinternals/downloads/procmon

1. Остановить запись (`Ctrl + E`), очистить список событий (`Ctrl + X`).
2. В фильтрах (`Ctrl + L`) добавить `Process Name is parent.exe → Include` и `Process Name is child.exe → Include`.
3. Возобновить запись (`Ctrl + E`), запустить программу с `input.txt`, затем остановить запись.
4. Открыть дерево процессов (`Ctrl + T`) и убедиться, что `child.exe` является дочерним для `parent.exe`.
5. Найти в журнале события `Process Create` / `Process Start`, `CreateFile`, `ReadFile`, `WriteFile`, `Process Exit`.

При выполнении опыта зафиксированы **PID 23264** для `parent.exe` и **PID 7272** для `child.exe`. Дерево процессов подтвердило связь родителя и потомка. В журнале наблюдались чтение `input.txt`, запись дочерним процессом в `\Device\NamedPipe` (так Process Monitor отображает операции с каналом), чтение родительским процессом из канала и завершение дочернего процесса.

Записи Process Monitor показывают операции ОС, но не обязательно дословные имена вызванных функций Win32 API. Поэтому, например, наличие `WriteFile` в журнале не означает, что в исходном коде `child.c` напрямую вызывается Win32-функция `WriteFile`: запись производится через стандартный поток `stdout`.

## Основные результаты

- Родительский процесс успешно создаёт дочерний и обменивается с ним данными через анонимный канал.
- Дочерний процесс обрабатывает четыре строки входного файла; получены суммы **60, 20, 50 и 42**.
- В консоль выводятся PID обоих процессов, что позволяет сопоставить запуск с событиями Process Monitor.
- Реализованы обработка ошибок, ожидание завершения дочернего процесса и закрытие используемых дескрипторов.

**Вывод:** освоены создание процесса с помощью Win32 API, перенаправление стандартных потоков и межпроцессное взаимодействие через `pipe`; работоспособность подтверждена запуском программы и диагностикой в Process Monitor.
